# OpenAnalytics on Dokploy

The blueprint in [`dokploy/`](dokploy/) deploys the complete stack as one
Dokploy Compose service: fourteen containers, four public hostnames, every
secret generated for you.

**Not a supported path yet, and — unlike [COOLIFY.md](COOLIFY.md) — not yet
written from an install that was done.** This file was written alongside the
blueprint for the `Dokploy/templates` catalogue submission, and its promises
are the compose file's promises until the first live install rewrites this
header. Where COOLIFY.md says "measured", this file can only say "designed".

## Before you start

- A Dokploy install you are an admin of. An **x86-64/amd64** server: the
  official images are published for that architecture only.
- **Four DNS records**, all pointing at that server. The dashboard, the api,
  the collector and the realtime stream are four hostnames, not four paths.
  See [SELF-HOSTING.md](../../SELF-HOSTING.md#four-names-and-why-it-is-four)
  for why.
- About 4 GB of RAM for the stack, on top of whatever Dokploy itself uses.
- **25 GB of free disk**, or 15 GB and `docker image prune -a -f` before each
  upgrade. A release is about 13 GB of images and an upgrade holds two
  generations at once.

## 1. Create the service

**Once the template is in the catalogue:** create a project, then **Templates**,
search for "Open Analytics", deploy.

**Before that (or to run a newer blueprint than the catalogue carries):**
create a **Compose** service, open **Advanced → Import**, and paste the
blueprint's Base64 config — the templates site renders it on the template card,
including on the PR preview URL while the submission is open.

Either way you get the same thing: the compose file, a `.env` filled with
generated passwords and secrets, the Caddyfile mount, and four generated
domains.

## 2. Domains, all four on the edge

The template generates four random subdomains, and every one of them points at
the `edge` service on port 80. That is deliberate: the edge is a Caddy
instance that deletes the client-settable identity headers
(`CF-Connecting-IP` and its family) before anything internal reads them.
Without it, any visitor could pick their own rate-limit bucket or write their
own country into your analytics. **Do not repoint a domain at a service
directly.**

To use real hostnames, change **both halves and keep them equal**:

1. In the **Domains** tab, replace the four generated hosts with yours —
   `app.<domain>`, `api.<domain>`, `c.<domain>`, `rt.<domain>` — HTTPS on.
2. In the **Environment** tab, set `APP_DOMAIN`, `API_DOMAIN`,
   `COLLECTOR_DOMAIN` and `REALTIME_DOMAIN` to the same four values.
3. Redeploy.

The second half is the one that gets forgotten. The api builds its auth
origin, its CORS allowlist and every link it hands out from those variables,
and the dashboard's browser bundle is rewritten from them at container start —
the Domains tab alone routes traffic to a stack that still believes its old
names.

## 3. Environment variables

Everything required is already filled: every password, every base64 secret,
the four domains. **Two things are deliberately not there.** The three signing
key pairs and the credential keyring are generated by the `keygen` one-shot
inside the stack and handed over as files, because no platform generator can
produce a keypair whose halves must match across two services.

The one variable worth editing is `OA_EMAIL_FROM`, the sender address on
outgoing mail. It is a from-address and not a lock: mail is configured later
from the dashboard under **Account → Deployment**, and a relay stored there
wins over anything in the environment. Magic links work regardless.

## 4. Deploy

The first deploy pulls twelve images — nine of ours, plus postgres, alpine and
caddy, about 2 GB — and downloads a 60 MB geo database. Nothing is built.

When it settles there are **fourteen containers and three of them have
exited**. That is success, not failure: `migrate`, `keygen` and `geoip` are
one-shot steps that do their work and stop. The other eleven stay up and go
healthy, `web` last.

Then open `https://app.<domain>`. A deployment nobody has signed into offers
to create the first account rather than asking you to sign in. **Do that
immediately.** The offer is open to whoever asks first and your DNS records
are public. It closes permanently the moment one account exists.

## Things that are true here and nowhere else

**The geo database is fetched for you, and it comes with a licence
condition.** The `geoip` one-shot downloads **DB-IP City Lite** on the first
deploy and never again. DB-IP and not MaxMind because of the licence: GeoLite2
needs an account and a licence key and forbids redistribution, while DB-IP
City Lite is [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/). **That
licence asks for credit wherever you show the data:**

> IP Geolocation by DB-IP, [https://db-ip.com](https://db-ip.com), used under
> CC BY 4.0.

The databases go stale within a month or two. To refresh, delete
`dbip-city-lite.mmdb` from the `geoip` volume and redeploy. To use MaxMind
instead, `docker cp` your own file into the collector's `/geoip` and point
`GEOIP_DB_PATH` at it. A failed download fails the deploy on purpose — the
collector refuses to start on a path that names no file, and the alternative
is a crash loop one step further from its cause. Redeploy to retry.

**The header rules live in the edge's Caddyfile, not in Traefik.** Dokploy's
Traefik owns TLS and writes `X-Forwarded-For` and `X-Real-Ip` from the
connection, but it passes `CF-Connecting-IP` and its family through. The
mounted Caddyfile deletes that family on every route that reaches the
collector, the api or the realtime stream. If you fork the blueprint, keep the
edge and keep the deletions.

**Every service gets only its own secrets, and that is enforced.** Each
service has a FORBIDDEN_KEYS list and exits at startup when handed a secret it
must not hold. If a service logs one line about a variable it "must not be
provided", that is the least-privilege boundary doing its job — the fix is
never to hand the variable to more services.

## Upgrades

The images are pinned in the compose file (`v0.4.2` today), so a redeploy
reinstalls the same release. To move: set `OA_IMAGE_TAG` in the Environment
tab to the release you mean and redeploy — migrations re-run idempotently, the
keygen and geoip one-shots short-circuit, and nothing regenerates behind your
back. Move it only when the release notes say the blueprint still matches; the
env shape and the migrations are versioned with the images. When the catalogue
template itself is bumped, a fresh import carries the new pin.

## If something is wrong

`docker logs` on the service that is unhealthy, first. The services say why
they refuse to start, on one line, on purpose: a missing variable, a path that
names no file, a secret a service is not allowed to hold.

If `web`, `api`, `gateway`, `collector` or `realtime` restarts a few times
right after the first deploy, look at what it is waiting for before blaming
it: each waits for `migrate` and `keygen` to finish and for its stores to be
healthy, and on a slow first pull that takes a minute. Convergence is the
design; a service still crash-looping ten minutes in is a real error with its
reason in the log.
